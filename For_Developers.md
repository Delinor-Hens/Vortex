## 1. Обзор архитектуры

Vortex состоит из трёх основных компонентов:

- **Ядро на C++ (`vortex_core.dll`)** – отвечает за сетевое взаимодействие с Ollama, HTTP-клиенты для облачных провайдеров, хранение чатов и настроек, шифрование ключей, генерацию ответов (включая потоковую).
- **Графический интерфейс на Python (Tkinter)** – обеспечивает пользовательский интерфейс, включая чат, редактор кода, вкладку плагинов, мини-игры, темы и агентский режим.
- **Установщик (`vortex_setup.exe`)** – написан на C++ (WinAPI), предназначен для развёртывания приложения на компьютере пользователя, установки Ollama, загрузки модели и создания ярлыков.

Связь между Python и C++ осуществляется через `ctypes` (файл `gui/core_wrapper.py`).

### 1.1. Взаимодействие компонентов

Python-интерфейс загружает `vortex_core.dll` и вызывает экспортируемые функции для:

- инициализации (`vortex_init`);
- управления чатами;
- отправки сообщений и получения ответов;
- потоковой генерации;
- работы с провайдерами;
- шифрования и хранения данных.

C++ DLL общается с Ollama по HTTP (порт 11434) или с облачными API через WinHTTP. Ответы возвращаются в Python в виде строк UTF-8.

### 1.2. Потоки выполнения

Все длительные операции (генерация ответа, запуск кода) выполняются в отдельных потоках, чтобы не блокировать графический интерфейс.

## 4. Сборка C++ DLL (vortex_core.dll)

Выполните в корне проекта (`Vortex/`) в **cmd** (не PowerShell):

    cd /d E:\Vortex
    g++ -shared -o build\vortex_core.dll core\src\api_bridge.cpp core\src\llm_engine.cpp core\src\memory_store.cpp core\src\text_processor.cpp core\src\providers.cpp -DVORTEX_CORE_EXPORTS -std=c++11 -mwindows -static-libgcc -static-libstdc++ -Wl,-Bstatic -lstdc++ -lwinpthread -Wl,-Bdynamic -lws2_32 -lwinhttp -lcrypt32 -Icore/include

### Пояснение флагов

- `-shared` – создать DLL.
- `-DVORTEX_CORE_EXPORTS` – макрос для экспорта функций.
- `-std=c++11` – стандарт C++.
- `-mwindows` – отключить консольное окно.
- `-static-libgcc -static-libstdc++` – встроить GCC-рантайм.
- `-Wl,-Bstatic -lstdc++ -lwinpthread -Wl,-Bdynamic` – статически слинковать libstdc++ и pthread (убирает зависимость от `libstdc++-6.dll` и `libwinpthread-1.dll`).
- `-lws2_32 -lwinhttp -lcrypt32` – системные библиотеки.
- `-Icore/include` – путь к заголовкам.

### Важные замечания

- Сборка должна выполняться в **cmd**, а не в PowerShell, так как PowerShell иначе интерпретирует символ `^` или флаги.
- Убедитесь, что папка `build` существует, иначе создайте её заранее: `mkdir build`.

## 5. Сборка автономного exe (PyInstaller)

    python -m PyInstaller --onefile --windowed --noconfirm --add-binary "build/vortex_core.dll;build" --add-data "assets;assets" --add-data "config.json;." vortex.py

**Примечания:**
- Не удаляйте папки `build` и `dist` перед сборкой, если в них есть нужные файлы.
- `--noconfirm` позволяет перезаписывать файлы без запросов.
- Результат: `dist\vortex.exe`.
- При использовании PyInstaller важно, чтобы все внешние файлы (DLL, assets, config) были добавлены корректно.

Если используется `vortex_launcher.cpp`, соберите его:

    g++ vortex_launcher.cpp -o Vortex.exe -municode -mwindows -static -lole32 -lshell32 -luuid -lshlwapi -lcomctl32

    g++ vortex_setup.cpp -o vortex_setup.exe -municode -mwindows -static -lole32 -lshell32 -luuid -lshlwapi -lcomctl32 -loleaut32 -lurlmon

## 9. Проверка зависимостей

После сборки DLL выполните:

    objdump -p build\vortex_core.dll | findstr "DLL Name"

**Должны остаться только системные DLL:**
- `KERNEL32.dll`
- `USER32.dll`
- `api-ms-win-crt-*`
- `WINHTTP.dll`
- `CRYPT32.dll`

**Не должно быть:**
- `libgcc_s_seh-1.dll`
- `libstdc++-6.dll`
- `libwinpthread-1.dll`

Аналогично проверьте `dist\vortex.exe` и `vortex_setup.exe`.

## 10. Агентский режим и генерация проектов

Агентский режим активируется галочкой **"Agent mode"** в вкладке "Код" (по умолчанию он включен всегда).  
Он работает по следующему алгоритму:

1. Пользователь вводит задачу и язык.
2. Модель получает запрос: *"Напиши полный код программы на языке X, решающий задачу Y. Верни только код. Никаких пояснений."*
3. Во время генерации агент принудительно включает режим `thinking` (неограниченная длина ответа).
4. Ответ очищается от markdown-обёрток и сохраняется в файл `main.<ext>` внутри папки `Projects/project_<timestamp>`.
5. Код загружается в редактор, но **не запускается автоматически**.
6. Пользователь может запустить программу вручную кнопкой «▶ Запустить» или «▶ Запустить код из поля». При запуске в стандартный ввод передаётся пустая строка, чтобы программы с `input()` не падали с `EOFError`.
7. Если программа завершилась с ошибкой (Traceback, SyntaxError и т.п.), активируется кнопка **«🛠 Исправить»**. При нажатии агент отправляет текст ошибки модели и получает исправленный код, который записывается в тот же файл и загружается в редактор.
8. Пользователь видит подробный отчёт о каждом шаге.

Все проекты сохраняются в папке `Projects` рядом с исполняемым файлом.

## 12. Работа с изображениями и файлами

Пользователь может прикреплять изображения и текстовые файлы.

- Изображения кодируются в base64 и отправляются в Ollama (поле `images`).
- Текстовые файлы читаются и добавляются в промпт.
- Для облачных провайдеров изображения пока не поддерживаются (только Ollama).

Реализация находится в `gui/main_window.py` (кнопка 📎) и `core_wrapper.py` (метод `send_message_with_images`).

### 12.1. Поддерживаемые форматы изображений

## 15. Шифрование API-ключей

API-ключи провайдеров хранятся в зашифрованном виде с помощью Windows DPAPI (`CryptProtectData` / `CryptUnprotectData`).

- При загрузке ключ расшифровывается.
- Реализация в `core/src/memory_store.cpp`.

## 17. Часто встречающиеся ошибки

### 17.1. `libgcc_s_seh-1.dll not found`
**Причина:** динамическая линковка GCC-рантайма.  
**Решение:** использовать `-static-libgcc -static-libstdc++` (см. раздел 4).

### 17.2. `libwinpthread-1.dll not found`
**Причина:** не статически слинкована библиотека pthread.  
**Решение:** добавить `-Wl,-Bstatic -lwinpthread -Wl,-Bdynamic`.

### 17.3. `0xc00000ff` при запуске
**Причина:** использование `std::locale("")` в `memory_store.cpp`.  
**Решение:** удалить все вызовы `file.imbue(...)`.

### 17.4. `api-ms-win-crt-*` отсутствует
**Причина:** нет Universal C Runtime.  
**Решение:** установить Visual C++ Redistributable (установщик делает это автоматически).

### 17.5. `Модель не успела загрузиться`
**Причина:** слишком маленький таймаут.  
**Решение:** в `llm_engine.cpp` увеличено число попыток до 10 и пауза до 10 секунд.

### 17.6. `не удалось разобрать JSON` в агентском режиме
**Решение:** агентский режим теперь не требует JSON. Он просто запрашивает код и сохраняет его в файл.

## 18. Дополнительные технические детали

### 18.1. Работа с Ollama

Vortex обращается к Ollama по HTTP на `127.0.0.1:11434`. Используются endpoints:

- `/api/tags` – получение списка моделей.
- `/api/generate` – генерация ответа (с параметрами `num_predict`, `temperature`, `top_p`, `stream`, `think`).

### 18.2. Режимы генерации

Параметры по умолчанию:

| Режим   | num_predict | temperature | top_p |
|---------|-------------|-------------|-------|
| instant | 128         | 0.8         | 0.9   |
| normal  | 256         | 0.6         | 0.9   |
| thinking| -1 (без ограничения) | 0.3 | 0.9   |

### 18.3. Обработка Unicode

При получении ответа от Ollama или облачных провайдеров выполняется декодирование escape-последовательностей `\uXXXX` в UTF-8. Это решает проблему с символами типа `>=`, которые могли приходить как `\u003e=`.

### 18.4. Потоковая генерация

Для потокового режима используется HTTP-ответ с `Transfer-Encoding: chunked` или просто с разделением строк `\n`. Каждая строка разбирается, извлекается поле `response`, и чанк передаётся в Python-интерфейс. Буфер чтения в C++ увеличен до 16 КБ для ускорения.

## 19. Тестирование и отладка

### 19.1. Логирование

Для отладки можно включить вывод в консоль. В Python-интерфейсе уже есть отладочные сообщения в `core_wrapper.py`. В C++ при необходимости можно добавить `OutputDebugString` или запись в файл.

### 19.2. Тестовые сценарии

- Проверка генерации короткого кода.
- Проверка генерации длинного кода (например, игра на Pygame).
- Проверка, что `input()` не вызывает `EOFError`.
- Проверка ручного исправления ошибок.
- Проверка потоковой выдачи: чанки идут слитно, без лишних переносов.
